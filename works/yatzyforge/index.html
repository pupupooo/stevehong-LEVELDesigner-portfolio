[SEC.01: PRODUCTION_PIPELINE]

一、从 HTML 原型到 Godot 测试包的制作流程

这个项目的工作方式更接近一条可追踪的生产链路：先把设计判断写成规格，再让 AI 进入明确的任务边界。仓库中保留了 `AGENTS.md` / `CLAUDE.md` / `TASKS.md` / `CHECKPOINTS.md` / `CHANGELOG.md`，用来约束多对话、多工具并行时最容易发生的上下文漂移。

1. 先建立“文档真源”，再让 AI 写代码

项目约定 Codex 更像指挥台：负责拆任务、排优先级、整理设计规格和验收 checkpoint；Claude Code 更像实现工位：按规格改 Godot 代码、运行验证并记录结果。所有机制变化必须先回到 `design/` 或 `TASKS.md`，避免代码里长出没有被设计承认的“幽灵机制”。

这里选择文档作为真源，主要是因为游戏原型的“正确”不只存在于代码行为里。代码能说明某个商品如何结算，却很难说明为什么这次要验证“关键骰面组”、为什么飞轮不能早于点火器、为什么某个 UI 反馈要服务玩家复述 build。对 AI 来说，代码上下文会诱导它优先补实现、修局部 bug、顺手扩机制；文档真源则把设计意图、取舍边界和验收问题放在更高一层，先规定“这轮允许改变什么、不能改变什么”。

这个约束在小项目里看似笨重，但它让 AI 协作变得可控：当商店、骰面、符号、刻印、目标分和 UI 反馈同时变化时，我能追溯每一次修改的设计依据，也能把下一轮任务继续分发给不同工具。

2. 用 HTML MVP 验证基本循环，再迁移到 Godot

早期版本先用单文件 HTML / Three.js 做出可玩的快艇骰子改造原型，验证投掷、锁骰、计分、倍率和基础视觉反馈。v0.2 后项目主线迁移到 Godot 4.6.2，用 GDScript 重建核心逻辑、场景和 UI，目标转为可稳定试玩、可截图评审、可录屏展示的 MVP。

Godot 工程按层拆分：`scripts/core/` 放纯玩法逻辑，`scripts/controllers/` 负责流程编排，`scripts/views/` 承担 3D 骰子、UI 和反馈动画。这个拆分让 AI 更容易在明确边界内修改，也方便用 headless check 和 smoke tests 做机械回归。

3. v0.5 的核心切片：关键骰面组

在 v0.4.6 阶段，项目已经能跑通资源骰、得分骰、目标分、商店和 8 关结构，但试玩反馈指出“构筑感知弱”。因此 v0.5 暂停继续堆泛用倍率，把设计主语收束为“关键骰面组”。玩家应该能在一局结束后说出：我这局靠哪几个骰面赢，为什么它们是一组。

  • 点火器：点数雕刻、符号烙印、精准烙印、银边 / 金边刻印、重铸骰面，让普通骰面第一次变成关键面。
  • 飞轮：复制骰面、复制符号、复制刻印、复制点数，让已经成型的关键面扩散成一组。
  • 符号与刻印：符号负责条件触发，刻印负责结算放大，主动符号池收束为 coin / star / gear / mirror。

4. 用 Build Lab 做构筑和曲线模拟

v0.5 之前还做了一个 Build Lab，定位是设计实验台，用来查看、讨论、编辑和可视化构筑体系。它读取 `design/build_lab/*.json`，把 archetypes、items、boss rules、curve targets 放到一个单文件 HTML 工具里，支持比较 8 关目标分曲线、录入模拟器报告、检查道具是否真的服务某条 build 路线。

这个工具也遵守单向流动：Build Lab 只服务设计讨论，不直接写入 Godot，不生成 GDScript。比如当前 `curve_targets.json` 中记录了 200 局模拟后的 20.5% 胜率和死亡关卡分布；这些数据会先回到设计规格，确认目标分或商品池调整方向，再进入实现任务。

5. 验证和打包也进入流程

Godot 项目中有 `tools/run_smoke_tests.gd` 和 `tools/package_release.sh`。v0.5.0-test.1 的 Packaging Pass 会先执行 headless check，再导出 macOS / Windows 包，整理 zip，并写入 SHA256。最近一次记录中，smoke tests 达到 1026 passed、0 failed，Windows 包也确认同时包含 exe 与 pck。

这套流程让我能把“AI 帮我做了一个原型”推进到更可验证的表达：有规格、有切片、有自动检查、有可下载包，也有明确的已知债务，例如飞轮两段 picker 仍是最小可玩 UI、多骰 Arc Line 仍需聚合表达。

[SEC.01B: WORKFLOW_SUMMARY]
01 / SPEC SOURCE

文档先行

用设计规格、任务面板和 checkpoint 约束 AI 修改范围，保证机制、数值和 UI 语义都有可追溯来源。

02 / GODOT SLICE

分层实现

将核心规则、流程控制和表现层拆开，让 Codex / Claude Code 可以围绕明确模块推进 Godot 纵切。

03 / BUILD LAB

构筑模拟

用 Build Lab 管理 archetypes、items、目标曲线和模拟器报告，让 build 假设先经过设计实验台再进入 Godot。

[SEC.02: GAME_DESIGN]

二、核心设计：让玩家感觉自己在“锻造”五颗骰子

战斗与计分

每回合投掷、锁定骰子，并选择可提交的牌型计分。快艇骰子的熟悉结构降低理解成本，肉鸽构筑提供变化。

骰面改造

点火器 / 飞轮作为当前版本的两类改造入口，让玩家逐步把普通骰面变成自己的核心引擎。

8 关原型流程

用短流程验证循环、成长节奏和失败反馈，避免过早扩内容，把制作压力集中在可读性和决策密度上。

测试包目标

v0.5.0-test.1 的验收问题很具体：玩家能否在一局结束后说出自己的关键骰面组，以及第一个飞轮商品是否帮助它成型。

[VALIDATION TARGETS]

这个 Prototype 当前最重要的验证问题：

  • 理解：玩家能否明白资源骰 / 得分骰的核心循环。
  • 拥有感：玩家能否感受到“我在改造这 5 颗骰子”。
  • 复盘：玩家一局结束后能否说出自己靠哪组关键骰面赢。
